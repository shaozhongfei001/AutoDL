# SDD 06 — 开发工作流 Loop Engineering（CodeBuddy 长程任务多阶段迭代契约）

> **状态：MANDATORY**（强制）。本契约规范 CodeBuddy 在本项目进行 SDD 开发时，
> 如何通过**无人干预的多阶段开发 Loop**，把一个长程大任务逐步规划、执行、
> 验证、反馈并引向成功交付。区别于 `05_LOOP_ENGINEERING.md`（运行时训练循环），
> 本文针对**开发过程本身**。

## 1. 定义

**开发工作流 Loop Engineering** = CodeBuddy 把一个长程开发任务分解为
**多个有序阶段**，每个阶段构成一个独立的**开发 Loop**：

```
┌─ 阶段 Loop ────────────────────────────────────────────┐
│  ① 规划(PLAN) → ② 执行(EXEC) → ③ 验证(CHECK)          │
│     → ④ 反馈/自愈(REFLECT) → ⑤ 门禁判定(GATE)          │
│                ↑______________│ (进入下一阶段)          │
└────────────────────────────────────────────────────────┘
多阶段 Loop 逐级推进，使长程大任务最终成功交付。
```

每个阶段 Loop 结束于一个**门禁(GATE)**：通过则进入下一阶段；失败则自愈
（重试/修正/降级/回退）后重入本阶段或回退上一阶段。

## 2. 阶段划分原则

- 长程任务必须显式划分为**有序阶段**（Phase 0..N），每阶段有：
  - **目标(Objective)**：本阶段要交付的可验证成果。
  - **范围(Scope)**：允许触碰的文件/模块。
  - **验收(Exit Criteria)**：进入下一阶段的机器可判定条件。
  - **预算(Budget)**：时间/资源/API 调用上限。
- 阶段间有**依赖顺序**；允许回退（前一阶段成果不满足时）。
- 单阶段规模必须**可控**（避免超大阶段导致难以验证）。

## 2a. 阶段规划产出物模板（PHASE PLAN）

每个阶段启动前，CodeBuddy 必须产出并维护一份 **PHASE PLAN**（写入
`contracts/phases/<task_id>/PHASE_<N>_PLAN.md` 或等价位置），字段如下：

```yaml
phase_id: "P2"                 # 有序阶段号
task_id: "<长程任务 ID>"
objective: "本阶段要交付的可验证成果（一句话）"
dependencies: ["P1"]            # 前置阶段，缺失则阻塞
scope:
  allow: ["core/loop.py", "tests/test_loop.py"]   # 允许触碰的文件/模块
  deny: ["core/experiment_contract.py"]           # 禁止触碰（文件所有权隔离）
acceptance:                     # Exit Criteria（机器可判定，进入下一阶段依据）
  - "pytest tests/ -q 全部通过"
  - "新增测试覆盖 X 行为"
  - "无 lint 错误"
  - "基准回归测试未劣化"
budget:
  max_cycles: 3                 # 本阶段最多重试 Loop 次数
  max_api_calls: 100             # 本阶段 LLM 调用上限
  max_wall_seconds: 1800         # 本阶段最大墙钟（无人值守保护）
subagents:                       # 是否派发 SubAgent 及分工
  enabled: true
  ownership:
    - agent: "le-x"
      files: ["core/foo.py", "tests/test_foo.py"]
    - agent: "le-y"
      files: ["core/bar.py"]
exit_on_fail: "retry_up_to_3_then_replan"  # 见无人值守执行协议
```

**必填字段**：`objective`、`scope.allow`、`acceptance`（≥2 条可判定）、
`budget`。缺少任一项即视为阶段规划不完整，禁止进入 EXEC。

## 3. 每阶段开发 Loop 的 5 步

### 3.1 ① PLAN — 规划
- 依据 SDD 契约（当前 Gate）解析本阶段目标、范围、验收。
- 产出本阶段任务清单（todos），并明确**可验证的出口判据**。
- 规划是否需派发 SubAgent 及分工（文件所有权隔离，避免冲突）。

### 3.2 ② EXEC — 执行
- 按任务清单实施代码/文档/配置改动。
- 多 SubAgent 协作时：按**文件所有权**分配，避免同一文件多 agent 写。
- 遵循现有架构与契约（受保护边界、命名、风格）。

### 3.3 ③ CHECK — 验证
- 运行完整测试套件（`pytest`）确保无回归。
- 运行本阶段新增的针对性测试。
- lint 检查（无新增错误）。
- 验证验收判据是否满足。

### 3.4 ④ REFLECT — 反馈与自愈
- 对比"实际产出 vs 阶段目标"，识别差距。
- **自愈决策**：
  - 成功 → 固化成果，进入门禁。
  - 小偏差 → 本阶段内修正后重入 CHECK。
  - 大偏差/阻塞 → 降级范围 / 回退上一阶段 / 请求人类介入（仅当真正无法推进时）。

### 3.5 ⑤ GATE — 门禁判定
- 依据 Exit Criteria 机器判定 PASS / FAIL。
- PASS → 记录阶段成果（commit + 状态更新），进入下一阶段。
- FAIL → 记录原因，触发 REFLECT 自愈。

## 4. 无人值守执行规范

- **不打断**：在多阶段 Loop 执行中，除非触发"请求人工介入"判定（见 §4a），
  否则 CodeBuddy 应自主完成各阶段，不向用户逐阶段请示。
- **批量汇总**：多 SubAgent 协作时，收集全部结果后一次性汇报，不中途碎片汇报。
- **保留成果**：每个阶段 PASS 后 commit 并更新 `PROJECT_STATUS.yaml`，即使后续
  发现方向调整，已交付成果可回退/复用。
- **安全降级**：某 SubAgent 未完成时，主 Agent 应能接管其成果或降级范围，不阻塞整体。

## 4a. 无人值守执行协议（如何决定是否请求人工介入）

> **目标**：最大化无人值守推进，仅在"真正无法自行推进"时才请求人工。
> 采用**阶梯式自主决策**：先自愈，再降级，最后才请求人工。

### 阶梯 0 — 自愈（默认，不打断）
遇到可自行解决的问题，直接处理并继续，不询问：
- 工具调用失败（网络/超时）→ 重试（指数退避）。
- 单元测试失败 → 定位并修复代码，重跑直至通过。
- lint 错误 → 修复。
- 子任务阻塞但可换路径 → 改用等价方案。
- 缺少非关键信息 → 基于合理假设继续，并在汇总中注明假设。

### 阶梯 1 — 阶段内降级（仍不打断）
自愈无法解决，但可通过**调整本阶段范围/方式**继续推进：
- 某功能依赖未就绪 → 本阶段先实现独立可测的部分，标记依赖项为下阶段。
- SubAgent 未完成 → 主 Agent 接管其文件所有权继续。
- 验收标准部分满足 → 明确记录未满足项，降级范围后 PASS（需在 GATE 记录）。

### 阶梯 2 — 回退（仍在 Loop 内）
降级后仍无法达成，且判断为**前置阶段成果有误**：
- 回退上一阶段，修正其成果后重入本阶段（阶段状态机支持回退边）。

### 阶梯 3 — 请求人工介入（仅在下列硬阻塞触发，中断无人值守）
只有以下**穷尽式条件**之一满足，才向用户请求介入：
1. **缺不可推断的关键凭据/权限**：如 API key、密钥、明确访问权限，且无任何
   合法替代路径。
2. **需求冲突无法自决**：存在两条以上互斥且影响交付方向的合理解读，且任意
   选择都会产生不可逆成本（如删除数据、破坏性 git、大范围重写）。
3. **方向性变更需授权**：任务要求超出原定范围，需用户明确批准（如新增付费
   资源、改变产品方向）。
4. **自愈+降级+回退均已耗尽**：同一阶段重试达 `budget.max_cycles`，且所有
   自愈/降级/回退路径尝试完毕仍失败。
5. **安全隐患**：检测到可能导致数据丢失/泄露/不可逆损坏的操作，需用户确认。

### 请求人工介入的规范
- 仅在满足上述 5 条件之一时触发；触发前必须**先完成阶梯 0/1/2**。
- 请求时**打包上下文**：当前阶段、已尝试的自愈动作、剩余选项、需要的具体决策，
  让用户一次性给到可执行指令，避免来回。
- 用户给出决策后，CodeBuddy 据此继续推进，不再就同一问题重复打断。

## 5. 阶段状态机

```
PHASE_N_OPEN → (PLAN) → (EXEC) → (CHECK) → (REFLECT)
   ↑  FAIL/回退           │  PASS
   │                      ▼
   └──────────────────  GATE PASS → PHASE_{N+1}_OPEN → ... → DELIVERED
```

状态：`OPEN → IN_PROGRESS → CHECKING → PASSED/FAILED → (NEXT_OPEN)`

## 6. 无人值守准入（Gate）

开启本机制（长程多阶段无人值守开发）前必须：
- [ ] 长程任务已完成阶段划分（Phase 0..N，含目标/范围/验收/预算）
- [ ] 每阶段 Exit Criteria 可机器判定
- [ ] 每阶段测试与回归基线已明确
- [ ] SubAgent 分工文件所有权已隔离
- [ ] 已定义自愈/回退/降级策略

## 7. 与 SDD 门禁的映射

| 开发 Loop 阶段 | SDD 门禁（04） |
|---|---|
| 长程任务总规划 | Gate 0/1（证据闭合、合同批准） |
| 每阶段 PLAN | 阶段目标 → 对应合同/ADR |
| 每阶段 EXEC+CHECK | 实现 + QA Gate 2 |
| 每阶段 REFLECT+GATE | 集成/回归 QA |
| 最终交付 | 生产就绪 / 24x7 准入门禁 |

## 8. 验收（QA）

| ID | 检查项 |
|----|--------|
| DLE-01 | 长程任务被显式划分为多个有序阶段，每阶段有目标/范围/验收/预算 |
| DLE-01a | 每阶段启动前产出 **PHASE PLAN**（§2a 模板），必填字段完整，否则禁止 EXEC |
| DLE-02 | 每阶段是完整 PLAN→EXEC→CHECK→REFLECT→GATE 闭环 |
| DLE-03 | 无人值守下多阶段自动推进，不逐阶段打断用户 |
| DLE-03a | 遵循阶梯式无人值守协议（§4a）：自愈→降级→回退，仅 5 种硬阻塞才请求人工 |
| DLE-04 | 阶段 PASS 后成果固化（commit+状态更新） |
| DLE-05 | 阶段 FAIL 触发自愈（修正/降级/回退），不静默跳过 |
| DLE-06 | 多 SubAgent 文件所有权隔离，无写冲突 |
| DLE-07 | 最终长程任务经多阶段 Loop 达到交付（Exit Criteria 全满足） |

**入口**：阶段 Loop 启动即执行 `①PLAN` 产出 PHASE PLAN → 校验必填字段 →
通过后才进入 EXEC；任一必填字段缺失则阶段不得启动（回退到规划）。
